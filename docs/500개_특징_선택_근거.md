# 왜 500개 특징을 선택했는지

> 팀원 전달용. 특징 추출 모듈이 최종적으로 몇 개의, 어떤 특징을 뽑아야 하는지의 근거 문서입니다.

## 한 줄 결론

> EMBER 2568개 특징 전체를 쓴 모델과, 상위 500개만 쓴 모델의 성능이 **거의 같거나 오히려 500개가 미세하게 더 좋았습니다.** 그래서 최종 특징 개수를 **500개**로 확정합니다.

---

## 평가 지표 설명 (Threshold / FPR / TPR / ROC-AUC)

결과표를 보시기 전에, 여기 쓰인 용어부터 짧게 설명드릴게요.

**Threshold(임계값)** — 모델은 "악성일 확률 0.73" 같은 0~1 사이 점수를 뱉습니다. 이 점수를 "악성/정상" 둘 중 하나로 확정하려면 기준선이 필요한데, 그 기준선이 threshold입니다.
```
점수 >= threshold → 악성 판정
점수 <  threshold → 정상 판정
```

**FPR(False Positive Rate, 오탐율)** — 실제로는 정상인 파일을 악성이라고 잘못 판정한 비율. 낮을수록 좋습니다.

**TPR(True Positive Rate, 탐지율)** — 실제 악성 파일을 악성이라고 맞게 잡아낸 비율. 흔히 말하는 "Recall"과 같은 개념입니다. 높을수록 좋습니다.

**ROC-AUC** — threshold와 무관하게, 모델이 정상/악성을 전반적으로 얼마나 잘 구분하는지 나타내는 종합 점수(0.5=랜덤, 1.0=완벽).

**왜 정확도(Accuracy) 대신 이 조합을 쓰는가** — threshold를 낮추면 TPR은 올라가지만 FPR도 같이 올라가는 트레이드오프 관계라, 아무 기준 없이 "TPR이 높다"고만 말하면 오탐도 같이 늘었을 수 있어 신뢰할 수 없습니다. 그래서 **"FPR을 0.1%까지만 허용하겠다"고 먼저 고정**하고, 그 조건에서 TPR이 얼마나 나오는지를 비교합니다. 또한 이 데이터는 정상:악성 비율이 50:50으로 맞춰져 있어 실제 운영 환경 비율과 다르기 때문에, Accuracy나 F1은 배포 시 성능을 제대로 예측하지 못해 사용하지 않습니다.

Threshold 자체는 **calibration(보정용) 데이터에서만 산출**하고, 그 threshold를 eval(별도 시간대 데이터)에 적용해서 TPR을 확인하는 방식으로, 같은 데이터로 기준을 정하고 채점하는 반칙(누수)을 방지했습니다.

## 실험 방법

LightGBM으로 특징 개수를 다르게(100개, 500개, 1000개, 전체 2568개) 해서 각각 모델을 학습시키고, 위에서 설명한 기준(ROC-AUC + 고정 오탐율 0.1%에서의 탐지율)으로 비교했습니다.

## 결과

| 특징 개수 | ROC-AUC | 탐지율(TPR @ FPR 0.1%) |
|---|---|---|
| 100개 | 0.9942 | 80.01% |
| **500개** | 0.9952 | **82.77%** ← 최고점 |
| 1000개 | 0.9952 | 82.72% |
| 전체(2568개) | 0.9953 | 82.51% |

100개에서 500개로 늘릴 때는 성능이 뚜렷하게 좋아지지만(80.0% → 82.8%), 500개 이후로는 더 늘려도 성능이 그대로거나 오히려 살짝 떨어집니다. **500개가 "더 늘려도 소용없어지는 지점"입니다.**

## 500개면 특징 추출 모듈에 실질적으로 무슨 의미인가

- 전체(2568개) 대비 **80.5% 감소**한 개수입니다
- 특징을 뽑는 로직이 그만큼 가벼워지고, 실시간 API 응답 속도에도 유리합니다
- SHAP 근거 계산도 특징 수에 비례해서 느려지는데, 500개면 훨씬 빠릅니다

## 이 500개는 "어떻게" 골라진 것인가 (선택 기준)

LightGBM이 학습 후 자동으로 계산해주는 **Feature Importance**(각 특징이 판정에 얼마나 기여했는지 점수)로 순위를 매겨, 상위 500개를 선택했습니다.

- **1차 기준(split)**: 이 특징이 트리에서 분기 기준으로 몇 번 쓰였는지
- **2차 교차검증(gain)**: 이 특징이 분기할 때마다 오차를 실제로 얼마나 줄였는지

두 기준으로 뽑은 상위 500개 중 **379개(75.8%)가 겹치는 것을 확인**해, 어느 기준으로 봐도 대체로 비슷한 특징들이 중요하다는 걸 교차 검증했습니다.

## ⚠️ 상욱님이 알아두셔야 할 중요한 제약 — "정확한 500개 목록"이 아닙니다

이 500개는 **EMBER가 미리 해싱해서 만들어둔 벡터 안에서의 순위**입니다. 이 중 일부(Import/Export/Section 관련 블록)는 **여러 API 이름이 하나의 칸에 뒤섞여 있어서(해싱), "정확히 어떤 API인지" 역추적이 불가능**합니다.

thrember 소스(`features.py`)를 직접 확인해 500개를 정확한 블록으로 분류한 결과:

| 구분 | 개수 | 비율 |
|---|---|---|
| 해싱 안 됨 (정확한 계산식 재현 가능) | 303개 | 60.6% |
| 해싱됨 (카테고리 힌트로만 활용) | 197개 | 39.4% |

**상세 스키마와 블록별 분류 결과는 `feature_schema.md`를 참고해주세요.** 그 문서 안에 PE Header, Entropy, StringExtractor(신규 발견 카테고리) 등 해싱 안 된 부분은 정확한 계산 방식까지 정리해뒀고, API/DLL처럼 해싱된 부분은 도메인 지식으로 독립 설계하도록 안내해뒀습니다.
